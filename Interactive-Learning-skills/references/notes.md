# 最终 Markdown 笔记规范与质检

## 内容边界

笔记是独立成品，不是聊天总结。正文包含：

1. 章节定位及学习目标（可简述）
2. 问题背景与设计目的、实际意义
3. 定义、关键概念与技术边界
4. 完整架构与各组件职责
5. 端到端流程和关键数据/控制路径
6. 真实场景与实操（含正确命令及验证）
7. 排障诊断与处理原则
8. 注意事项、易混淆点与总结

按技术主题灵活组织，不强制每篇写八个机械标题；但不能漏重要知识。

## 风格

- 用规范而易懂的中文，循序渐进；尽量一段解释清楚一个难点。
- 优先用简洁表格比较概念；必要时用流程图、拓扑图、带注释的命令块。
- 输出可复制到语雀的标准 Markdown，标题层级规范，代码块注明语言。
- 正文不得出现聊天式措辞或指向用户提供材料的出处话术，如“根据教材/课件/文件/第 25 页”“你刚才答错”“前文讨论过”。
- 允许在独立附录中单独列技术参考链接；不要把资料出处写入知识讲解正文。
- 如用户提出“错误步骤不要写”，仅保留可验证的正确步骤，排障章节可以列故障现象和错误原因，但不能给错误操作当推荐。

## 章末 CLI 规定

- 本节或本章讲解中出现 CLI 命令时，在章末设置「CLI 速查与参数解析」。保留讲过的可执行命令，说明用途、关键参数、执行前提、预期结果及验证方式。没有讲过 CLI 的章节可省略。

- 命令与注释放在同一个可复制的代码块里。单行命令须在紧接的下一行用 `#` 逐项按列对齐标注工具、各级子命令、参数名及对应值、位置参数。可合并标注紧密相连的选项和值，例如在 `-f qcow2` 下写「源格式=qcow2」。另用一行简述整条命令的用途及预期结果。多行命令在完整命令之后逐项标注，注释行不要接在续行反斜杠之后。

## 图片

- 能帮助理解设备外观、物理链路、关键拓扑、组件交互时加图；简单定义无需强制图片。
- 首选原创/准确的 Mermaid 架构图或流程图；需要真实设备照片时注明链接来源，不伪造。
- Markdown 图片使用相对路径 `![描述](images/name.png)`，打包时确保图片真实存在；如没有图片资源，改 Mermaid，不留失效链接。
- 解释图中所有关键箭头、图例和层次，颜色不应是理解的唯一依据。

## 错题处理

用户犯过的错误不以“用户错题”混入正文。将正确认识放到“常见误区”；错题映射/掌握情况可单独存为复习附录，不影响笔记作为独立文章阅读。

## 发布前检查

- 每个专业术语首次出现时是否有解释？
- 每个重要组件是否讲到“为什么有它”和“在什么时候工作”？
- 端到端流程是否与架构图一致？
- 有无版本不适用的命令、依赖、API 路径？
- 是否解释预期结果、验证方法、风险？
- 是否有资料不支持的自造事实？
- 标题、表格、代码、Mermaid 语法、图片路径是否合理？
- 正文是否完全去掉对话残留、教材出处话术、错误操作步骤？
